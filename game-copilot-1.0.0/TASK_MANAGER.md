# 작업 관리자 (2번) + 1.0.3 취소·연결 관리 (3번)

3단계는 기존 TaskManager를 변경하지 않고 `copilot/task_control.py`에서 원격 시작/진행/취소/유지 신호/결과 조회를 연결합니다.
전송 규격과 원격 감시기 조건은 `TASK_CANCEL_PROTOCOL.md`, 적용법과 시험은 `PATCH_3_README.md`를 보세요.

copilot/tasks.py는 게임과 모델에 독립적인 작업 상태 관리 모듈입니다.
작업을 실제로 조작하는 실행기나 백그라운드 스케줄러는 포함하지 않습니다.

## 상태

| 상태 | 의미 | 다음 작업 가능 |
|---|---|---|
| starting | 고유 작업 ID를 만들고 실행을 요청하는 단계 | 아니오 |
| accepted | 실행기가 요청을 접수함. 성공 확인은 아님 | 아니오 |
| running | 실행기가 진행 중이라고 보고함 | 아니오 |
| cancel_requested | 취소 의도를 기록함. 원격 중단 확인은 아님 | 아니오 |
| unknown | 통신 오류/시간 초과 등으로 결과를 모름 | 아니오 |
| succeeded | 실행기로부터 성공 확인 | 예 |
| failed | 실행기로부터 실패 확인 | 예 |
| cancelled | 실행기로부터 중단 확인, 또는 전달 전 로컬 취소 | 예 |

취소 요청 후 성공 확인이 올 수도 있습니다. 이때 실제 결과는 성공으로 기록합니다.
결과 불명은 종료 상태가 아닙니다. 새 작업을 막고 같은 작업 ID의 확인 결과를 기다립니다.

## 모듈 인터페이스

- begin(game_id, action_id, revision, timeout=30): 한 작업을 예약하고 고유 task_id를 반환.
- update(task_id, status, sequence, progress=None, message=''): 실행 결과 보고.
- request_cancel(): 취소 의도 기록만 수행. 게임에 네트워크 요청을 보내지 않음.
- mark_unknown(task_id): 실행 결과를 모르는 상태로 전환.
- expire(): 현재 시각과 deadline을 비교하여 초과 시 unknown으로 전환.
- snapshot(), history(): 현재 작업과 최근 완료 작업 최대 50개의 복사본.
- ensure_idle(): 미완료 작업이 있으면 다음 실행/연결 차단.

update는 accepted/running/succeeded/failed/cancelled를 받습니다.
sequence는 작업별로 증가하는 0 이상의 정수이며 로컬 취소/시간 초과는 이 번호를 소모하지 않습니다.
진행률은 0~1 또는 None이고 감소시키지 않습니다. 성공 시 1이 됩니다.
다른 작업 ID, 오래된/중복 sequence, 확정 종료 후 도착한 응답은 무시합니다.
모든 상태 변경은 잠금으로 보호하며 반환값과 이벤트는 복사본입니다.
모델의 '성공했을 것'이라는 추측으로 update를 호출하면 안 됩니다.

expire는 호출한 시점에만 동작합니다. 실제 장기 실행기는 주기적으로 호출해야 하며,
시간 초과 자체는 게임 동작을 중단하지 않습니다. 3단계 TaskControl은 이를 감지해 원격 취소를 요청하고 유지 신호를 중단합니다.

## 기존 엔진과 연결

현재 /v1/action은 '게임 적용까지 완료한 응답'이라는 기존 계약을 유지합니다.
Engine.execute는 최신 상태 검증 후 task_id를 만들고 같은 값을 request_id로 전달합니다.
유효한 v1 완료 응답이면 accepted → succeeded를 기록합니다.
단순 접수만 확인하는 미래의 장기 작업 응답에 이 경로를 재사용하면 안 됩니다.

응답 손실/잘못된 확인 응답은 unknown 처리하고 같은 실행 세션에서 추가 행동과 재연결을 차단합니다.
명확한 실패 확인이 없는 HTTP 오류도 보수적으로 unknown입니다. 자동 재시도하지 않습니다.
중지 전에 전달되지 않은 작업은 로컬에서 cancelled로 확정할 수 있습니다.
이미 전달된 작업은 취소 요청만 기록하며, 늦은 성공 확인을 거짓 취소로 바꾸지 않습니다.

진행 로그에 ID 앞 8자리와 상태/진행률을 표시합니다. 전용 작업 관리 화면은 후속 단계입니다.
실시간 브리지는 1번과 동일하게 조언 전용입니다. 취소 가능한 턴제 장기 작업은 별도 `/v1/tasks/*` 경로를 사용하며, 접수 응답으로 succeeded를 기록하지 않습니다.

## 세션과 재시작

작업 기록은 메모리에만 있습니다. 프로그램 종료 후 자동 복구/재개하지 않습니다.
결과 불명인 채로 프로그램을 재시작한다고 기존 게임 동작이 취소되는 것은 아닙니다.
3단계의 `작업 결과 확인` 버튼은 지원 모듈에 동일 ID의 결과를 읽기 전용으로 조회합니다.
기존 v1 단발 실행에는 이 조회 규격이 없으므로 해당 결과 불명은 실제 게임에서 적용/중단 여부를 확인해야 합니다.
키/프로필 파일 형식과 저장 위치는 바꾸지 않았습니다.

## 모의 검증

python -m examples.task_lifecycle_demo

API 없이 작업 접수, 진행, 성공, 실패, 취소 확인, 결과 불명과 중복 시작 차단을 출력합니다.
게임 동작을 수행하는 데모는 아닙니다. 단발 행동의 통합 확인은 기존 데모 게임을 사용합니다.
